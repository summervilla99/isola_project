# ISOLA 개발 기획서

> 바다 위 작은 섬에서, 내가 좋아하는 것들로 나를 표현하고 친구의 세계를 방문한다.

- 문서 버전: 1.0 · 작성일: 2026-10-28
- 문서 성격: 제품 정의, MVP 구현 명세, 확장 설계, 검수 기준을 겸하는 Codex 개발 입력 문서
- 서비스명: **ISOLA(이솔라)**. 이탈리아어로 섬을 뜻하며, 2026-10-28 사용자 확정.
- 대상: 기획자, 디자이너, 개발자, 코딩 에이전트
- 근거: 제공된 대화에서 확인 가능한 사용자 구상과 이번 요청. 과거 답변 본문은 복원되지 않아 내용을 추정해 인용하지 않았다.
- 아래 수량·일정·성능 예산은 **초기 제품 결정 및 검증 목표**다. 측정 결과나 이미 구현된 기능을 뜻하지 않는다.

## 1. 제품 개요

ISOLA는 4~8명의 친구가 함께 머무는 초대 전용 섬 기반 취향 아카이빙 서비스다. 섬은 바다, 나무, 풀, 꽃, 석양이 있는 따뜻한 공간이다. 각 사용자는 자기 집과 정원을 꾸미고, 책·영화·문장·위스키를 작은 오브젝트로 전시한다. 친구의 집에 귀여운 3D 아바타로 방문해 기록을 읽고 댓글을 남긴다.

핵심 가치는 경쟁, 수집 압박, 접속 시간 보상이 아니라 **자기표현, 취향의 발견, 친밀한 비동기 교류**다. 집은 단순한 장식 화면이 아니라 개인 아카이브의 공간적 인터페이스다.

### 1.1 확정할 초기 기본값

| 항목 | 결정 |
|---|---|
| 이용 기기 | 데스크톱 웹, 모바일 웹, 설치 가능한 PWA |
| 그래픽 | 고정에 가까운 쿼터뷰, 로우폴리 3D, 직교 카메라 |
| 섬 정원 | 최대 8명, 권장 4~8명. 1명부터 시작 가능 |
| 소속 | MVP에서는 사용자당 활성 섬 1개 |
| 공간 | 사용자당 집 내부 1개 + 개인 정원 1개 |
| 관계 | 섬 멤버가 친구 역할을 한다. 별도 친구 신청 시스템 없음 |
| 공개 범위 | 초대 전용. 인터넷 전체 공개 없음 |
| 핵심 상호작용 | 내 캐릭터 이동, 공간 감상, 아카이브 열람, 댓글 |
| MVP 접속 모델 | 비동기. 다른 사용자의 현재 위치는 표시하지 않음 |
| 수익화 | MVP에 결제·재화·유료 아이템 없음 |
| AI | MVP 실행 경로에 LLM 호출과 3D 생성 모델을 넣지 않음 |
| 서비스 언어 | 한국어 우선, 문자열 분리로 다국어 확장 대비 |

### 1.2 대표 사용자와 사용 이유

- 자신의 책, 영화, 문장 기록을 건조한 목록 대신 작은 방에 모으고 싶은 사람.
- 단체 채팅에 매번 말을 걸지 않아도 친구의 요즘 취향을 알고 싶은 4~8명의 모임.
- 현실의 외모나 성별 규범과 관계없이 원하는 모습으로 편히 존재하고 싶은 사람.

대표 장면: 사용자가 최근 읽은 책을 등록하고 책장 슬롯에 놓는다. 다음 날 친구가 방문해 책을 눌러 짧은 감상을 읽고 “이 부분 나도 좋았어”라는 댓글을 남긴다. 사용자는 다음 접속 때 알림을 확인한다.

## 2. 성공 조건과 제품 원칙

### 2.1 MVP 성공 조건

1. 새 사용자가 10분 이내에 섬 생성 또는 가입, 아바타 설정, 첫 취향 등록, 첫 전시를 완료한다.
2. 초대한 친구가 별도 앱스토어 설치 없이 모바일 링크로 가입하고 방문한다.
3. 집주인이 접속하지 않아도 저장된 공간과 허용된 아카이브를 안정적으로 볼 수 있다.
4. 꾸미기 결과가 새로고침과 기기 변경 이후에도 유지된다.
5. 아바타 외형과 정체성은 서로 제약하지 않으며, 필수 성별 선택이 없다.
6. 3D를 사용하지 못하거나 원하지 않는 사용자도 목록 화면으로 기록, 방문, 댓글을 이용한다.

### 2.2 제품 지표

| 지표 | 정의 | 초기 검증 목표 |
|---|---|---|
| 첫 전시 전환 | 가입 후 24시간 내 첫 전시 완료 사용자 / 신규 사용자 | 60% 이상 |
| 초대 활성화 | 유효 초대 링크를 열고 7일 내 가입한 사람 / 링크 방문자 | 관측 후 기준 설정 |
| 주간 교류 | 주간 활성 섬 중 서로 다른 2명 이상이 방문 또는 댓글한 섬 비율 | 50% 이상 |
| 7일 재방문 | 첫 전시 사용자 중 7일 후 정한 관측 창에 재방문한 비율 | 파일럿 후 기준 설정 |
| 저장 신뢰성 | 정상 온라인 상태에서 성공한 저장 / 유효 저장 시도 | 99% 이상 |

전환율 목표는 사업 예측이 아닌 파일럿 가설이다. 방문자 이름을 집주인에게 자동 공개하는 기능은 넣지 않는다. 분석 이벤트에는 댓글 본문, 성별 표현, 취향 감상 원문을 전송하지 않는다.

## 3. 범위와 단계

### 3.1 Phase 1 — 출시 가능한 비동기 MVP

| 영역 | 포함 내용 | 완료 조건 |
|---|---|---|
| 계정 | 이메일 OTP 로그인, 로그아웃, 계정 삭제 요청 | 다른 기기에서 동일 데이터 복원 |
| 섬 | 생성, 초대, 가입, 멤버 조회, 탈퇴, 방장 이전·내보내기 | 동시 가입에도 정원 8명 초과 불가 |
| 아바타 | 체형·피부·머리·옷·액세서리·색상 조합 | 외형 옵션에 성별 잠금 없음 |
| 공간 | 고정 섬, 개인 정원, 집 내부, 집 간 이동 | 모바일에서 방문 가능 |
| 꾸미기 | 카탈로그 배치·회전·이동·삭제, 초안 저장·공개 | 잘못된 배치 서버 거부 |
| 아카이브 | 책·영화·문장·위스키 CRUD, 검색·필터, 전시 연결 | 원본 기록과 전시 오브젝트 분리 |
| 교류 | 집 방명록, 기록 댓글, 앱 내 알림 | 권한 밖 댓글 읽기·쓰기 불가 |
| 안전·설정 | 차단, 신고, 공개 범위, 접근성, 데이터 내보내기 | 권한 및 삭제 시나리오 통과 |
| PWA | manifest, 설치 안내, 오프라인 안내 화면 | 온라인 복귀 후 정상 사용 |

MVP 아트 범위는 공용 자연 테마 1개, 집 형태 1개, 가구·정원·전시 소품 합계 24개로 제한한다. 옷과 머리 등 아바타 부품은 별도 카탈로그로 관리한다. 출시용 에셋이 없어도 초기 수직 구현은 도형으로 완성한다.

### 3.2 Phase 1.5 — 관찰 후 개선

- 꾸미기 편의성, 테마 추가, 전시 슬롯 확대, 온보딩 개선.
- 동의한 사용자에게만 읽지 않은 알림 요약 또는 푸시 알림 검토.
- 동의 기반 AI 취향 정리 및 기존 에셋 배치 제안 실험.
- 실제 기기 성능 데이터에 따른 품질 단계 조정.

### 3.3 Phase 2 — 실시간 함께 머무르기

- 동일 섬·동일 공간에 있는 멤버의 아바타 표시와 이동 동기화.
- 인사·박수 등 제한된 이모트, 접속 상태 표시 선택.
- 재접속, 연결 손실, 차단, 권한 회수 처리.
- 꾸미기는 여전히 소유자 전용이며 공동 편집하지 않는다.

### 3.4 Phase 3 — 놀이와 창작 확장

- 릴레이 소설, 공동 정원 이벤트, 공동 전시 등 작은 협동 활동.
- 복수 섬, 외부 손님, 공유 공간 편집은 각각 별도 권한 설계 후 추가.
- 생성형 3D 에셋은 비용·저작권·검수·최적화 운영체계를 확보한 뒤 실험한다.

### 3.5 명시적 비범위

MVP에는 실시간 타인 이동, 실시간 채팅·음성, 전투, 낚시, 농사 경제, 거래, 마켓, 결제, 출석 보상, 공개 피드, 랭킹, 팔로워, 무작위 매칭, 네이티브 앱, VR, 자유 지형 편집, 사용자 3D 파일 업로드, 외부 도서·영화 API 연동, 사진 업로드, 자동 표지 수집, AI 공간 생성, 릴레이 소설을 구현하지 않는다.

## 4. 사용자 플로우

### 4.1 섬을 처음 만드는 사람

1. 랜딩에서 “내 작은 섬 시작하기” 선택.
2. 이메일 인증 → 닉네임 입력 → 기본 아바타 선택 또는 건너뛰기.
3. 섬 이름 입력 → 첫 집과 정원 자동 배정.
4. 짧은 안내로 이동, 오브젝트 선택, 목록 보기 경험.
5. 첫 취향을 입력하고 기본 전시 슬롯에 놓기.
6. 공간 공개 → 초대 링크 복사. 링크 공유는 사용자가 직접 수행한다.

온보딩은 언제든 나갔다 돌아올 수 있다. 진행 상태를 저장하고 이미 완료한 단계를 반복 강제하지 않는다.

### 4.2 초대받은 친구

1. 링크에서 초대 유효 여부와 초대자가 공개한 섬 이름만 확인.
2. 로그인 → 초대 상세 확인 → “이 섬에 함께 살기” 명시적 선택.
3. 서버 트랜잭션에서 정원·토큰·기존 소속 검증.
4. 빈 집터 자동 배정 → 아바타 설정 → 자신의 공간 진입.
5. 섬 지도에서 친구 집 선택 → 방문 → 기록 읽기 → 댓글 남기기.

만료·취소·정원 초과를 각각 설명한다. 다른 섬에 소속되어 있으면 먼저 기존 섬을 떠나야 한다고 안내한다. 가입을 시도한 것만으로 기존 소속을 삭제하지 않는다.

### 4.3 취향 기록과 전시

1. “취향 서랍”에서 유형 선택.
2. 제목 및 유형별 정보를 입력하고 감상·태그 작성.
3. 기본 공개 범위는 `나만 보기`. 저장 후 “섬 친구에게 공개하고 전시하기”를 별도로 선택.
4. 집 또는 정원의 전시 가능한 슬롯 선택.
5. 미리보기 → 공개 확인 → 장면 저장.
6. 친구가 소품을 선택하면 2D 상세 패널이 열린다.

비공개 기록은 전시할 수 없다. 공개 중인 기록을 비공개로 바꾸면 관련 전시는 즉시 비활성화하고 방문 화면에 원문·제목·댓글이 남지 않게 한다.

### 4.4 꾸미기

방문 모드 → 꾸미기 → 소품 선택 → 배치 미리보기 → 위치·회전 확정 → 초안 저장 → 공개. 저장 전 나갈 때는 “초안 저장 / 변경 버리기 / 계속 편집”을 제공한다. 네트워크 오류 시 저장되었다고 표시하지 않는다.

### 4.5 재방문

앱 열기 → 내 정원 → 읽지 않은 알림 확인 → 댓글이 있는 기록으로 이동 → 답글 대신 새 댓글 작성. MVP 댓글은 1단계 목록이며 중첩 답글은 없다.

### 4.6 탈퇴·방장 이전

- 일반 멤버 탈퇴: 확인 후 멤버십 종료, 집터 해제, 전시 공간 제거. 개인 취향 기록과 아바타는 개인 계정에 보존하고 기록은 비공개 전환한다.
- 다른 사람 공간에 작성한 댓글은 작성자에게 사전 안내 후 삭제 처리한다.
- 방장이고 다른 멤버가 있다면 방장 이전 후 탈퇴한다. 이전 대상은 현재 멤버만 가능하다.
- 마지막 멤버가 탈퇴하면 섬과 공간을 삭제한다.
- 새 섬 가입 시 빈 집·정원으로 시작하며, 보존된 개인 기록을 다시 선택하여 전시한다.

## 5. 기능별 상세 요구사항

### F01. 계정·프로필

- 닉네임 1~20자, 소개 0~160자. 닉네임은 전역 유일성을 요구하지 않는다.
- 이메일은 인증용 비공개 데이터이며 멤버 목록에 노출하지 않는다.
- 이메일 OTP 발급·검증에 서버 측 속도 제한을 적용한다.
- 프로필에는 선택적 호칭·대명사·자기소개를 둔다. 성별·출생 성별·의료 이력은 필수 입력하지 않는다.
- 정체성 표현 문구는 최대 60자의 선택적 자유 텍스트로 두고 공개 여부를 별도 설정한다.
- MTF, 논바이너리 등 사용자가 원하는 표현을 직접 사용할 수 있다. 시스템이 외형을 보고 추론하거나 자동 분류하지 않는다.
- 공개 프로필과 비공개 계정 설정은 다른 테이블/응답으로 분리한다.

### F02. 섬·초대·멤버 관리

- 섬 이름 1~30자, 설명 0~200자. 섬 생성자에게 `owner`, 나머지에게 `member` 역할 부여.
- 방장은 섬 이름 수정, 초대 발급·취소, 멤버 내보내기, 방장 이전만 가능하다. 타인의 집 편집·비공개 기록 열람 권한은 없다.
- 초대는 방장만 생성한다. 기본 7일 만료, 기본 최대 사용 7회, 필요하면 더 작은 횟수 선택.
- 토큰은 암호학적 난수로 만들고 DB에는 해시만 저장한다. 로그·분석 이벤트에는 원문을 남기지 않는다.
- 가입 시 섬 행 잠금 또는 동등한 직렬화 전략으로 멤버 수, 사용 횟수, 집터 할당을 한 트랜잭션에서 처리한다.
- 같은 사용자의 재요청은 멤버를 중복 생성하거나 토큰 횟수를 추가 차감하지 않는다.
- 방장은 자신을 내보낼 수 없다. 마지막 owner가 사라지는 변경은 서버가 거부한다.
- 집터 8개는 고정 배치한다. 비어 있는 집터는 식재가 있는 빈터로 표현한다.

### F03. 아바타

- 공통 리그를 사용하는 둥근 로우폴리 캐릭터. 신체 비율 선택 3종, 피부색 12종, 머리 6종, 상의 6종, 하의 4종, 액세서리 4종을 초기 목표로 한다.
- 모든 부품은 모든 체형에서 선택 가능하다. 조합 제약이 있다면 성별이 아닌 메시 호환성 문제로 처리하고 제작 과정에서 우선 해결한다.
- 기본 애니메이션은 idle, walk, wave 3개. MVP wave는 로컬 표현이다.
- 자유 슬라이더 대신 검증된 비율 프리셋을 제공한다. 색상도 초기에는 팔레트로 제한한다.
- 외형 저장 시 서버가 부품 ID, 호환 버전, 색상 허용값을 검사한다.
- MVP 방문 시 내 아바타만 걷는다. 집주인의 프로필 초상은 표시할 수 있지만 온라인 사용자처럼 움직이는 가짜 캐릭터는 배치하지 않는다.

### F04. 공간·이동

- 월드는 공용 섬 외부, 개인 정원, 개인 집 내부로 구분한다.
- 공용 섬은 고정 자연 배경이다. 정원 방문은 별도 인스턴스 장면을 로드하고, 집 내부는 문을 통해 전환한다.
- 집 내부를 분리 로드하여 전체 섬에 모든 가구를 동시에 렌더링하지 않는다.
- 데스크톱: 바닥 클릭/탭 이동, WASD·방향키 보조 이동, 접근 가능한 상호작용 버튼.
- 모바일: 바닥 탭 이동 기본. 카메라 드래그와 오브젝트 선택을 이동 임계값으로 구분한다. 가상 조이스틱은 MVP에 넣지 않는다.
- 고정 카메라 각도, 제한된 줌, “화면 가운데로” 버튼 제공. 자유 회전은 제외한다.
- 이동 경로는 그리드 A*로 계산하고 장애물·물·공간 경계를 피한다. 막힌 목적지는 가장 가까운 유효 셀로 보정하거나 이동 불가를 알린다.
- 사용자 간 충돌은 없으며 물리 엔진을 필수 의존성으로 두지 않는다.

### F05. 공간 꾸미기

- 집 내부 12×12, 정원 16×16 배치 셀. 1셀은 0.5 월드 단위, 아바타 높이는 약 1.5 단위로 제작한다.
- MVP 가구는 바닥 배치, 90도 단위 회전, 스케일 1 고정. 벽 부착물과 임의 수직 쌓기는 제외한다.
- 전시 소품은 가구의 이름 있는 슬롯에 붙인다. 테이블 위 자유 배치 대신 `shelf.slot_01` 같은 앵커를 사용한다.
- 각 공간 최대 배치 60개, 그중 전시 항목 최대 24개. 전시 소품도 총 배치 수에 포함한다.
- 배치 가능 여부를 색상과 텍스트로 함께 표시한다. 출입구 안전 영역, 통로, 가구 충돌, 경계, 슬롯 중복을 검사한다.
- 배치 순서에 따라 문에서 모든 주요 상호작용 지점까지 갈 수 있는지 탐색한다. 막힌 상태는 공개할 수 없다.
- 편집 중 되돌리기/다시 실행 최대 20단계는 클라이언트 메모리에서 제공한다.
- `초안 저장`은 내 편집본을 저장하며 방문자에게 영향을 주지 않는다. `공개`는 유효성 검사 후 공개 장면을 원자적으로 교체한다.
- 같은 계정이 두 탭에서 저장하면 revision으로 충돌을 감지한다. 조용히 덮어쓰지 않고 최신본 다시 불러오기와 변경안 보관을 안내한다.
- 즉시 저장은 명시적 저장 버튼으로 제공한다. 자동 저장은 MVP에 넣지 않는다.

### F06. 취향 아카이빙

공통 필드: 유형, 제목, 내 감상, 태그, 공개 범위, 생성·수정일. 제목은 1~120자, 감상은 최대 2,000자, 태그는 최대 5개·각 20자다. HTML 입력은 허용하지 않으며 일반 텍스트로 렌더링한다.

| 유형 | 추가 필드 | 전시 오브젝트 | 기본 정렬/표시 |
|---|---|---|---|
| 책 | 저자, 읽은 상태, 선택적 완독일 | 책·책등 | 제목·저자·내 감상 |
| 영화 | 감독, 선택적 개봉연도, 감상일 | 프레임·필름 소품 | 제목·감독·내 감상 |
| 문장 | 문장 본문 최대 500자, 출처, 선택적 쪽수 | 카드·작은 액자 | 문장·출처·내 메모 |
| 위스키 | 증류소/브랜드, 선택적 국가·도수·향미 메모 | 일반화한 병 소품 | 이름·향미·기억 |

- 위스키는 취향 기록 유형으로만 제공한다. 구매, 판매, 음주 챌린지나 추천 노출은 포함하지 않는다. 유형 숨기기 설정을 지원한다.
- 외부 링크는 선택 사항이며 HTTPS URL만 허용한다. 서버가 URL을 자동으로 가져오지 않는다.
- 책 표지·영화 포스터·상표 병 디자인은 자동 수집하지 않는다. 색상과 텍스트를 사용한 자체 디자인으로 표현한다.
- 필터: 유형, 태그, 공개 범위. 검색: 제목·저자/감독/출처·감상에 대한 기본 텍스트 검색. 페이지 크기 20개, 커서 페이지네이션.
- 하나의 기록을 여러 슬롯에 연결할 수 있지만, 같은 슬롯은 하나의 기록만 참조한다.
- 전시 삭제는 기록을 삭제하지 않는다. 기록 삭제는 모든 연결을 해제하고 관련 댓글도 삭제 처리한다.
- 공간에는 제목·감상 문자열을 복제 저장하지 않는다. 열람 시 권한 확인을 거쳐 최신 기록을 조회한다.
- 초기에 전체 계정당 기록 500개 한도를 둔다. 초과 시 데이터 손실 없이 안내하고 정책 변경 가능하게 설정값으로 관리한다.

### F07. 방문·댓글·알림

- 방문은 같은 섬의 활성 멤버만 가능하다. 자기 공간은 항상 열람 가능하다.
- 집과 정원 공개 범위는 각각 `나만 / 섬 멤버`. 최초 기본은 `나만`이며 온보딩에서 공개를 선택한다.
- 전시 기록 열람 조건은 **공간 공개 + 기록 공개 + 같은 섬 활성 멤버 + 차단 관계 없음**이다. 기록의 목록 열람은 기록 자체의 정책을 적용한다.
- 댓글 대상은 공간 방명록 또는 개별 아카이브다. 본문 1~500자, 링크 자동 미리보기 없음.
- 작성자는 수정·삭제 가능, 대상 소유자는 댓글 숨김 가능. 방장은 타인 공간의 댓글을 임의 수정하지 못한다.
- 공간 비공개 전환 시 그 공간 방명록 접근도 즉시 차단한다. 기록 댓글은 기록 공개 범위를 따른다.
- 같은 요청 ID의 댓글 생성은 한 번만 반영한다. 사용자당 분당 10개를 초기 속도 제한으로 둔다.
- 새 댓글 알림은 대상 소유자에게만 생성하며 자기 댓글은 제외한다. 알림에는 민감한 본문을 복사하지 않고 참조 ID와 유형만 둔다.
- MVP는 앱 진입 및 알림 패널 열기 시 조회한다. 항상 연결된 Realtime 구독은 필요 없다.
- 댓글 삭제, 차단, 탈퇴로 대상을 볼 수 없으면 알림도 숨기거나 삭제한다.

### F08. 차단·신고

- 차단은 양방향 상호작용 제한으로 작동한다. 두 사람은 서로의 개인 공간, 기록, 댓글, 프로필 상세를 볼 수 없다.
- 같은 섬의 최소 멤버 목록에는 집터 관리상 필요한 “표시 제한된 멤버” 자리표시자만 남긴다. 이메일·소개·외형·정체성은 제공하지 않는다.
- 공용 풍경 자체는 차단되지 않는다. Phase 2에서는 상대 Presence와 이동 이벤트도 차단해야 한다.
- 차단 후 기존 댓글과 알림도 읽기 시점에 필터링한다. 클라이언트 UI 숨김만으로 구현하지 않는다.
- 신고는 대상 ID·유형·사유·작성자·시각을 저장하며 일반 멤버와 방장이 신고 원문을 열람할 수 없다.
- 초기 운영은 별도 보호된 관리자 화면 또는 관리자 전용 도구로 처리한다. 신고 검토 담당자와 처리 경로가 없는 상태로 공개 출시하지 않는다.

### 6.2 시각 방향

- 섬은 바다 위에 떠 있는 평온한 공간으로, 둥근 지형과 부드러운 실루엣을 사용한다.
- 기본 시간대는 노을 직전의 골든아워. 실제 시간 동기화나 계절 시스템은 제외한다.
- 바다 `#8FCFD0`, 잎 `#86A875`, 크림 `#FFF7E8`, 석양 `#F2AD8D`, 기본 글자 `#25342D`를 출발 팔레트로 쓴다. 최종 대비는 조합별 검증한다.
- 저채도 자연 배경과 높은 가독성의 UI 패널을 분리한다. 텍스트를 복잡한 3D 배경에 직접 얹지 않는다.
- 나뭇잎·물결은 작은 움직임만 사용하고, 모션 감소 설정에서는 정지한다.
- 경쟁 게임처럼 체력바·재화 카운터·퀘스트 알림을 두지 않는다.

### 6.3 데스크톱·모바일

- 데스크톱은 3D 화면 + 오른쪽 상세 패널, 편집 시 왼쪽 카탈로그를 사용한다.
- 모바일은 하단 내비게이션 `섬 / 내 공간 / 취향 / 알림`과 바텀시트 상세 패널을 사용한다.
- 세로 화면을 기본 지원하고 가로 전환을 강제하지 않는다. 키보드가 열리면 입력 폼을 화면 안으로 유지한다.
- 버튼 터치 영역 최소 44×44 CSS px, 본문 16px 이상, safe area 여백 적용.
- 3D 화면 위 UI 조작은 이동 이벤트로 전파되지 않는다. 패널이 열리면 뒤쪽 이동을 일시 중지한다.
- 삭제·탈퇴·공개 범위 변경은 결과를 구체적으로 안내한다. 반복 저장 같은 일상 동작에는 확인 창을 남발하지 않는다.

### 6.4 빈 화면·실패 상태

| 상황 | 안내와 행동 |
|---|---|
| 첫 기록 없음 | “좋아하는 것 하나부터 놓아볼까요?” + 새 기록 |
| 공개된 전시 없음 | “아직 전시를 준비하고 있어요.” |
| WebGL 실패 | “목록으로도 공간을 둘러볼 수 있어요.” + 목록 전환 |
| 저장 오류 | 오류 이유, 재시도, 편집 내용 유지 |
| 저장 충돌 | 다른 창에서 변경되었음을 알리고 최신본 불러오기 |
| 권한 회수 | 현재 화면 데이터 제거 후 “이 공간에 접근할 수 없어요.” |
| 초대 만료 | “초대 기간이 끝났어요. 새 초대를 요청해 주세요.” |
| 오프라인 | 연결 복구 안내. 변경 요청은 비활성화 |

## 7. 기술 스택과 코드 구조

### 7.1 권장 구현안

| 계층 | 선택 | 용도 |
|---|---|---|
| 앱 | Next.js App Router + React + TypeScript | 라우팅, 인증 화면, API, 일반 UI |
| 3D | Three.js + React Three Fiber + Drei | 장면, 카메라, 모델, 선택·이동 |
| UI | CSS 변수 + Tailwind CSS + 접근 가능한 headless primitives | 디자인 토큰, 패널, 대화상자 |
| 로컬 상태 | Zustand | 편집 초안, 선택, 카메라, 세션 내 UI |
| 서버 상태 | TanStack Query | 조회 캐시, 저장 후 무효화, 오류 처리 |
| 입력 검증 | Zod | API 및 저장 데이터 스키마 |
| 백엔드 | Supabase Auth + PostgreSQL + Storage | 인증, 관계형 데이터, 권한, 파일 |
| 실시간 확장 | 서버 권한 검증 게이트웨이 + WebSocket, Supabase Realtime 후보 | Phase 2 위치·접속 이벤트 |
| 테스트 | Vitest, Testing Library, Playwright, SQL 권한 테스트 | 단위·통합·E2E |
| 배포 | Next.js 호환 호스팅 + 관리형 Supabase | 프리뷰·스테이징·운영 분리 |

버전 번호는 이 문서에서 고정하지 않는다. 구현 시작일에 공식 문서와 패키지 호환성을 확인하고 안정 버전을 lockfile에 고정한다. 3D Canvas는 클라이언트 전용으로 지연 로드하고 인증·목록 UI와 분리한다.

Next.js의 manifest 및 PWA 구성은 공식 가이드를 따른다. 자체 설계에서는 오프라인 데이터 편집과 푸시를 MVP에서 제외한다. [Next.js PWA 가이드](https://nextjs.org/docs/app/guides/progressive-web-apps)

### 7.2 책임 경계

- 브라우저: 렌더링, 입력, 미리보기 검증, 편집 초안.
- API: 인증, 권한 검사, 입력 검증, 속도 제한, 응답 최소화.
- DB: 소유권·멤버십 제약, 트랜잭션, revision, RLS 최종 보호.
- 자산 CDN/Storage: 검수된 공용 3D 에셋. 사용자 비공개 자료와 섞지 않는다.
- 클라이언트 저장 데이터는 신뢰하지 않는다. 좌표, asset ID, owner ID를 모두 서버에서 재검증한다.

## 8. 데이터 모델

모든 ID는 UUID, 시간은 UTC `timestamptz`로 저장하고 UI에서 사용자 시간대로 표시한다. 데이터 분리의 핵심은 **개인 원본 기록 / 공간 배치 / 멤버십 / 교류**를 독립적으로 관리하는 것이다.

| 테이블 | 주요 필드 | 제약·비고 |
|---|---|---|
| `profiles` | user_id, nickname, bio, avatar_config, avatar_version | 공개 필드만 포함 |
| `user_settings` | user_id, identity_text, identity_visibility, reduced_motion, quality, hide_whisky | 본인만 조회. 공개 프로필 응답에서 허용된 표현만 투영 |
| `islands` | id, name, description, owner_id, created_at | 소유자는 활성 멤버여야 함 |
| `island_members` | island_id, user_id, role, plot_index, joined_at | user_id unique, (island_id, plot_index) unique, plot 0~7 |
| `invites` | id, island_id, token_hash, expires_at, max_uses, used_count, revoked_at | token_hash unique, 원문 토큰 미저장 |
| `spaces` | id, island_id, owner_id, kind, visibility, schema_version | (owner_id, kind) unique; kind garden/interior |
| `space_drafts` | space_id, revision, placements_json, updated_at | 본인 전용, 공간당 초안 1개 |
| `space_publications` | space_id, revision, placements_json, published_at | 최신 공개본 1개, 원자적 교체 |
| `assets` | id, version, category, uri, footprint, slots_json, allowed_spaces, license_id | (id, version) unique; 임의 URL 불가 |
| `archive_items` | id, owner_id, type, title, note, metadata_json, visibility, revision | type별 metadata 검증, 사용자당 한도 |
| `archive_tags` | item_id, tag | (item_id, tag) unique |
| `exhibitions` | id, space_id, placement_id, archive_item_id | 공개본의 연결 인덱스, (space_id, placement_id) unique |
| `comments` | id, author_id, space_id?, archive_item_id?, body, revision, hidden_at, deleted_at | 두 대상 중 정확히 하나 필수 |
| `notifications` | id, recipient_id, actor_id, type, target_id, read_at | 댓글 본문 복제 금지 |
| `blocks` | blocker_id, blocked_id, created_at | 자기 차단 불가, pair unique |
| `reports` | id, reporter_id, target_type, target_id, reason, status, created_at | 일반 사용자는 자기 신고 접수 결과만 조회 |
| `request_dedup` | user_id, operation, key, response_ref, expires_at | 댓글·가입·공개 요청 중복 방지 |

### 8.1 정합성 규칙

- `owner_id`는 요청 본문을 신뢰하지 않고 인증 세션에서 결정한다.
- 공간 소유자는 해당 섬 활성 멤버여야 한다. 복합 FK 또는 트랜잭션 검증을 사용한다.
- 전시 연결의 기록과 공간 소유자가 같아야 한다. 다른 사람 기록을 임의로 내 집에 연결하지 못한다.
- `placements_json`은 레이아웃과 참조 ID만 포함한다. `exhibitions`는 공개 시 같은 트랜잭션에서 재생성하는 조회용 인덱스이며 독립 편집 API를 두지 않는다.
- 삭제·비공개 전환 시 공개 응답에서 전시 연결을 제거한다. 저장된 레이아웃에 오래된 ID가 있어도 원문 조회를 허용하지 않는다.
- 공간·기록·댓글 조회에 인덱스를 둔다: 멤버십 user_id/island_id, 기록 owner_id+updated_at+id, 댓글 target+created_at+id, 알림 recipient_id+created_at+id.
- 멤버 수 상한은 단순 클라이언트 검사로 보장할 수 없다. 가입·내보내기·방장 이전·탈퇴를 DB 함수 또는 동등한 원자적 트랜잭션으로 처리한다.
- 멤버 역할과 islands.owner_id 변경은 하나의 연산으로 묶고 owner가 정확히 한 명임을 보장한다.

  "spaceId": "11111111-1111-4111-8111-111111111111",

    {

### 9.2 제작 규칙

- 포맷 GLB/glTF, Y-up, 일관된 실제 크기와 피벗. 원점은 가구 바닥 중앙.
- 텍스처보다 vertex color와 공유 재질 우선. 필요한 텍스처는 기본 512px, 예외 1024px 이하.
- 에셋 ID, 버전, 저작자, 사용 허가, 출처, triangle 수, 압축 크기, collider footprint, 슬롯, 미리보기 경로를 manifest에 기록한다.
- 에셋 압축은 meshopt/KTX2 등 지원 가능성을 실제 기기에서 검증한 뒤 적용한다. 디코더 로딩 비용도 측정한다.
- 런타임 충돌체는 렌더 메시 대신 단순 그리드 footprint를 사용한다.
- 반복 자연물은 instancing, 공통 재질은 공유한다. 전시 텍스트는 3D 고해상도 텍스처 대신 선택 후 DOM 패널로 읽는다.
- 아바타 파츠는 공통 skeleton과 검증된 본 이름을 공유한다. 파츠별 rig 불일치를 런타임에서 억지로 보정하지 않는다.
- 모델 로딩 실패 시 대체 도형을 보여주고 상호작용·목록은 유지한다.
- 공용 에셋 URI에 버전을 포함해 캐시한다. 기존 저장 공간을 깨는 덮어쓰기를 금지한다.

### 9.3 초기 에셋 예산

| 대상 | 목표 |
|---|---|
| 가구·정원·전시 카탈로그 | 24개: 가구 10, 정원 10, 기록 유형 소품 4 |
| 아바타 1명 | 화면상 총 10k triangles 이하 목표 |
| 모바일 활성 장면 | 150k triangles 이하, draw calls 100 이하 목표 |
| 모바일 초기 필수 전송 | 앱·장면·아바타 포함 압축 합계 5MB 이하 목표 |
| 최초 장면 이후 추가 공간 | 공간별 증분 에셋 3MB 이하 목표 |
| 텍스처 GPU 추정 사용 | 활성 장면 합계 64MB 이하 목표 |

위 숫자는 합격을 위한 초기 예산이며 성능이 자동 보장된다는 뜻은 아니다. GPU 메모리 추정은 압축 파일 크기와 다르므로 에셋 리포트에서 별도로 계산한다.

## 10. 모바일·PWA·성능

### 10.1 품질 단계

| 항목 | 낮음 | 보통 | 높음 |
|---|---|---|---|
| DPR 상한 | 1.0 | 1.5 | 2.0 |
| 그림자 | blob shadow | 제한된 저해상도 | 단일 광원 그림자 |
| 풀·꽃 밀도 | 30% | 60% | 100% |
| 물결 | 정적 또는 단순 shader | 저빈도 | 기본 애니메이션 |
| 후처리 | 없음 | 없음 | 선택적, 성능 검증 후 |

- 모바일 초기값은 낮음 또는 보통. 저성능 감지 시 하향하고 사용자가 직접 변경할 수 있다.
- 프레임마다 React 상태를 갱신하지 않는다. 아바타 이동은 렌더 루프와 mutable ref에서 처리한다.
- 장면이 정지했으면 on-demand 렌더링을 활용한다. idle 애니메이션·물결이 켜져 있는 동안에는 필요한 프레임만 요청한다.
- 탭 비활성화 시 렌더링·오디오를 중단한다. 재진입 시 경과 시간 폭주를 clamp한다.
- 페이지 이동 때 geometry, material, texture, 이벤트 리스너를 적절히 해제한다. 공유 자산은 참조 수명에 따라 관리한다.
- React Three Fiber 공식 성능 문서의 instancing과 수요 기반 렌더링 방식을 구현 시 참고한다. [성능 가이드](https://r3f.docs.pmnd.rs/next/advanced/scaling-performance)

### 10.2 PWA 범위와 캐시 정책

- manifest에 name, short_name, icons, theme_color, start_url, standalone 표시를 정의한다.
- HTTPS에서 제공하고 브라우저별 설치 안내를 별도로 검수한다. iOS/Android의 설치 UI가 같다고 가정하지 않는다.
- 서비스 워커는 공개 앱 셸·버전 고정 공용 에셋만 캐시한다.
- 인증 API, 초대 토큰 페이지, 개인 기록, 댓글, 공간 데이터는 서비스 워커 저장 대상에서 제외한다.
- 오프라인에서는 안내 화면과 공개 앱 셸만 제공한다. 과거 방문한 친구의 비공개 데이터를 오프라인에서 열람하게 하지 않는다.
- 연결이 끊겨도 현재 편집 메모리는 유지하지만 새로고침 이후 복원을 보장하지 않는다. 이 제한을 UI에 명확히 알린다.
- 백그라운드 동기화, 오프라인 변경 큐, 웹 푸시는 MVP 비범위다.
- 새 버전 발견 시 편집 중 강제 새로고침하지 않는다. 저장 후 업데이트 안내를 제공한다.
- 로그아웃·계정 변경 시 Query 캐시와 개인 메모리 상태를 모두 비운다.

### 10.3 성능 합격 목표

- 390×844 모바일 뷰포트, 10Mbps/지연 100ms의 지정 프로필에서 앱 셸 LCP p75 2.5초 이하, 첫 3D 조작 가능 p75 5초 이하를 목표로 한다.
- 실제 중급 모바일 기기에서 60개 배치 공간을 60초 걸을 때 프레임 시간 p95 33ms 이하를 목표로 한다.
- 데스크톱 기본 장면은 60fps 목표. 지속 하락 시 품질을 자동 조정한다.
- 공간 전환 20회 후 메모리의 지속 증가나 WebGL context 반복 손실이 없어야 한다.
- 시뮬레이터 수치만으로 통과하지 않는다. 최소 iPhone 12급 실기기와 Galaxy A54급 실기기를 확보하거나 동급 대체 기기 모델을 기록한다.
- 미달 시 자연물 밀도·그림자·텍스처·동시 로딩 범위를 순서대로 줄인다. 접근성과 저장 정확도를 희생하지 않는다.

## 11. 프라이버시·권한·접근성

### 11.1 권한 표

| 행동 | 본인 | 같은 섬 멤버 | 방장 | 외부 사용자 |
|---|---|---|---|---|
| 내 비공개 기록·초안 | 읽기/쓰기 | 불가 | 타인 자료 불가 | 불가 |
| 공개 공간·기록 | 읽기/쓰기 | 읽기, 차단 관계 제외 | 멤버와 동일 | 불가 |
| 내 공간 편집 | 가능 | 불가 | 타인 공간 불가 | 불가 |
| 댓글 작성 | 가능 | 대상 접근 가능 시 | 멤버와 동일 | 불가 |
| 댓글 수정 | 자기 댓글 | 자기 댓글 | 자기 댓글 | 불가 |
| 댓글 숨김 | 대상 소유자 | 불가 | 타인 대상 불가 | 불가 |
| 초대·내보내기 | 방장일 때 | 불가 | 가능 | 불가 |
| 신고 검토 | 불가 | 불가 | 불가 | 불가 |

신고 검토는 별도 운영 권한이다. 사용자 계정의 섬 역할과 운영 권한을 혼용하지 않는다.

### 11.2 보안 구현 기준

- 사용자 데이터가 있는 노출 스키마 테이블은 RLS를 활성화한다. API 검사와 별개로 SQL 권한 테스트를 작성한다. [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)
- 서비스 역할 키는 서버 비밀 환경에만 둔다. 일반 사용자 요청은 가능하면 사용자 JWT와 RLS로 실행한다.
- 권한 상승이 필요한 DB 함수는 실행 권한·고정 search_path·입력 검증을 명시하고 최소 범위로 제한한다.
- 쿠키 기반 변경 요청은 Origin 및 CSRF 방어를 적용한다. 인증 세션 만료·갱신을 처리한다.
- 입력은 서버 스키마 검증, 문자열 출력은 이스케이프, 링크는 프로토콜 allowlist를 적용한다.
- 비공개 응답에 `Cache-Control: private, no-store`를 적용하고 공유 CDN 캐시 대상에서 제외한다.
- 개인정보·토큰·댓글 본문이 오류 로그에 남지 않도록 로그 필드를 allowlist로 정의한다.
- 타인 데이터 ID를 바꿔 요청하는 수평 권한 상승, 초대 무차별 시도, 속도 제한 우회를 테스트한다.

### 11.3 데이터 수명

- 계정 내보내기는 내 프로필·아바타·기록·배치·내가 작성한 댓글을 JSON으로 제공한다. 다른 사람의 비공개 정보는 제외한다.
- 계정 삭제 요청 시 즉시 세션과 접근 권한을 끊고, 앱의 활성 DB 데이터는 7일 이내 제거하는 정책을 초기 목표로 한다.
- 백업 잔존 기간은 인프라 설정을 실제 확인한 뒤 개인정보 안내에 적는다. 확인 전 완전 삭제 일정을 보장하지 않는다.
- 탈퇴·내보내기는 계정 삭제와 구분한다. 내보내기 대상 사용자의 공간을 제거하고 개인 기록을 비공개로 돌린다.
- 신고 증거 등 별도 보관 필요 데이터는 목적·기간·접근자를 정해 최소화한다. 이 문서는 법률 자문이나 특정 지역 법규 준수 판정이 아니다.

### 11.4 접근성

- 전체 기능에 키보드 접근과 명확한 focus ring을 제공한다.
- Canvas에만 핵심 정보를 넣지 않는다. 공간의 전시 목록, 이동 대상 목록, 기록 상세, 댓글을 DOM으로 제공한다.
- 목록 모드에서도 공간 방문, 기록 읽기·쓰기, 댓글을 완료할 수 있어야 한다. 꾸미기에는 좌표·회전·슬롯을 폼으로 지정하는 대안을 둔다.
- 모션 감소 설정은 카메라 트윈·물결·idle 움직임을 줄인다. 소리는 기본 꺼짐이며 사용자 동작 후 재생한다.
- 오류·공개 범위·배치 가능 여부는 색상만으로 전달하지 않는다.
- 일반 텍스트 대비 4.5:1 이상을 목표로 하고 200% 확대에서도 필수 조작이 가능해야 한다.
- 대화상자 포커스 이동·복귀, 바텀시트 닫기, 스크린리더 레이블과 저장 상태 알림을 검수한다.

## 12. API 계약

### 12.1 공통 규약

- `/api/v1` 경로, JSON, 서버 인증 필수. 예외는 로그인과 최소 초대 유효성 확인이다.
- 성공: `{ "data": ..., "meta": { "requestId": "..." } }`
- 오류: `{ "error": { "code": "...", "message": "...", "fieldErrors": {} }, "requestId": "..." }`
- HTTP: 400 입력 오류, 401 인증 필요, 403 허용된 객체의 작업 권한 부족, 404 존재하지 않거나 열람 불가, 409 revision/정원/소속 충돌, 429 제한, 500 서버 오류.
- 존재 자체를 숨겨야 하는 타인 공간·기록은 404로 통일한다.
- 쓰기 payload 최대 128KB, 조회 목록 20개 기본·50개 최대. 좌표는 정수 셀로 제한한다.
- 생성 재시도에는 `Idempotency-Key`를 사용하고 사용자·작업별로 24시간 보관한다. 같은 키에 다른 본문이면 409.

### 12.3 Phase 2 Realtime 계약

MVP는 HTTP만으로 완성한다. 실시간 기능은 영구 데이터 저장과 별도로 추가한다.

- 위치 토픽은 `space:{spaceId}`. 공용 섬 토픽은 `island:{islandId}`로 분리한다.
- 이벤트: `presence.join`, `presence.leave`, `avatar.move`, `avatar.emote`, `session.revoked`.
- 이동 payload: `v, sessionId, seq, position[x,z], yaw, state`. 사용자 ID와 room ID는 서버 인증 세션에서 붙인다.
- 클라이언트 전송 상한 10Hz, 서버 fan-out 상한 10Hz를 초기값으로 한다. 수신 측은 약 100ms 보간 버퍼를 사용한다.
- 서버가 최대 속도·좌표 범위·sequence·메시지 크기·space 접근 권한을 검증한다. 브라우저가 보낸 identity를 신뢰하지 않는다.
- 이동은 DB에 매 프레임 저장하지 않는다. 장면·기록·댓글 변경은 기존 API와 DB를 통과한다.
- 끊김 10초 후 타인 아바타 제거, 재접속은 지수 백오프와 jitter. HTTP 공개본을 재조회하고 허가된 위치에서 복귀한다.
- 내보내기·차단·비공개 전환 시 세션 강제 회수와 기존 구독 차단을 처리한다. 채널 이름이 비밀이라는 가정으로 보호하지 않는다.
- 특히 차단된 멤버가 섞인 방에서는 방 전체 broadcast가 위치를 누출할 수 있다. 서버에서 수신자별 필터링하거나 사용자별 권한 채널을 사용한다.

Supabase Broadcast/Presence를 선택하면 `realtime.messages`의 별도 권한 정책을 설계한다. 일반 업무 테이블의 RLS만으로 실시간 채널 권한이 자동 완성된다고 가정하지 않는다. [Realtime Authorization 문서](https://supabase.com/docs/guides/realtime/authorization)

구현 전 스파이크에서 즉시 권한 회수와 수신자별 필터를 검증한다. 이를 충족하지 못하면 인증된 WebSocket 게이트웨이를 별도 배치한다. 서버리스 HTTP 함수가 장기 WebSocket 연결까지 제공한다고 가정하지 말고 호스팅 지원을 확인한다.

## 13. AI와 운영 비용 설계

### 13.1 MVP 비용 원칙

MVP에서는 미리 만든 에셋을 조합하므로 방문·이동·꾸미기에 LLM 토큰 비용이 발생하지 않는다. 주요 비용은 앱 호스팅, DB, 인증 메일, 에셋 전송량, 로그·모니터링이다. 무료 플랜 사용 가능성은 구현 시점의 조건을 확인해야 하며 무료 운영을 보장하지 않는다.

월비용 추정식:

```text
호스팅 기본료 + DB/Storage 기본료
+ 과금 대상 에셋 전송 GB × 실제 단가
+ 인증 메일·실시간 메시지·로그 등 종량 사용량
+ 선택적 AI 입력/출력 토큰 비용
```

규모 검토 예시: 100명 × 월 20회 방문 × 세션당 평균 신규 전송 3MB = 약 6GB 전송. 이는 캐시·프리페치·장면 이동 횟수에 따라 바뀌는 단순 가정이며 견적이 아니다. 실시간 단계에서는 동시 연결 수와 이동 fan-out을 별도로 계산한다.

### 13.2 후속 AI 범위

1. 사용자가 직접 선택한 메모를 제목·유형·태그로 구조화한다.
2. “노을이 보이는 책 많은 방”을 기존 카탈로그 ID와 좌표를 사용하는 배치 제안 JSON으로 변환한다.
3. 서버가 소유권·에셋 허용값·수량·충돌·이동 경로를 검증한다.
4. 미리보기를 보여주고 사용자가 적용해야 초안이 바뀐다. AI 응답으로 공개본을 직접 변경하지 않는다.
5. 개인 기록 전송은 명시적 선택과 안내를 거친다. 성별 표현·댓글·다른 사용자의 기록을 자동 포함하지 않는다.
6. 요청당 입력 길이·출력 토큰·재시도 1회·일일 횟수 제한을 설정하고 관리자 예산 상한을 둔다.
7. 프롬프트와 결과는 버전 관리하며, 캐시 키는 사용자 범위·카탈로그 버전·입력 해시를 포함한다. 사용자 간 비공개 응답 캐시를 공유하지 않는다.

생성형 3D는 추론 비용 외에도 재생성, 리깅, 메시 정리, 충돌체 제작, 모바일 최적화, 부적절한 결과 검수 비용이 크므로 카탈로그 조합 방식의 효과를 검증한 후 도입한다.

## 14. 개발 마일스톤

일정은 숙련 개발자 1명과 코딩 에이전트, 제한된 아트 지원을 가정한 **8~10주 추정**이다. 에셋 확보·실기기 검증·배포 계정 준비에 따라 달라진다. 날짜보다 완료 게이트를 우선한다.

| 단계 | 예상 | 산출물 | 완료 게이트 |
|---|---|---|---|
| M0. 설계·스파이크 | 3~4일 | ADR, 권한 표, 도형 기반 모바일 3D, 에셋 예산 | 모바일 이동·목록 대안 가능 |
| M1. 기반 | 1주 | 앱·인증·DB migration·RLS·시드·CI | 두 계정 간 격리 검증 |
| M2. 핵심 수직 구현 | 1~1.5주 | 섬 생성→기록→전시→친구 방문→댓글 | 실제 DB로 전체 흐름 완료 |
| M3. 공간·아바타 | 1.5~2주 | 아바타, 꾸미기, 초안·공개, 정원·실내 | 저장 충돌·배치 검증 통과 |
| M4. 멤버·교류·안전 | 1주 | 초대, 탈퇴, 방장 이전, 차단·신고·알림 | 동시 가입·권한 회수 통과 |
| M5. 모바일·PWA | 1주 | 저품질 모드, 캐시 정책, 설치, 접근성 | 실기기·키보드·오프라인 검수 |
| M6. 파일럿·출시 | 1~1.5주 | 4~8명 테스트, 오류 수정, 운영 문서 | 핵심 결함 없음, 지표 수집 가능 |

### 14.1 M2 수직 구현 범위

처음에는 책 유형 1개, 집 내부 1개, 기본 아바타 1개, 책장·책·의자 3개 도형 에셋만 사용한다. 실제 인증·권한·저장·친구 댓글을 끝까지 연결한다. 이후 유형과 에셋을 확장한다. 시각적 데모만 완성하고 저장·권한을 뒤로 미루지 않는다.

### 14.2 각 단계 필수 산출물

- 실행 가능한 코드와 설정 예제. 비밀 값은 `.env.example`에 넣지 않는다.
- 순서 있는 migration과 테스트용 seed. 운영 데이터 초기화 명령은 자동 실행하지 않는다.
- 완료 항목·미완료 항목·검증 결과를 기록한 개발 노트.
- 재현 방법, 환경 변수 설명, 로컬 실행·배포·롤백 절차.
- 에셋 라이선스 목록과 성능 리포트.

| T13 | 방장 이전·탈퇴 경쟁 요청 | owner 정확히 1명 또는 섬 삭제, 고아 데이터 없음 |

| T15 | HTML/스크립트 포함 기록·댓글 | 텍스트 출력, 실행 없음 |
| T16 | 네트워크 단절 중 저장 | 성공 표시 없음, 현재 편집 유지 |
| T17 | 로그아웃 후 다른 계정 로그인 | 이전 계정 캐시·내용 노출 없음 |
| T18 | WebGL 실패·키보드만 사용 | 목록 대안으로 기록·댓글·배치 가능 |
| T19 | PWA 오프라인·버전 업데이트 | 안내 표시, 편집 중 강제 새로고침 없음 |
| T20 | 계정 내보내기·삭제 | 본인 범위만 내보내고 삭제 정책대로 처리 |
| T21 | 에셋 누락·구버전 장면 | 대체 도형 또는 명시적 오류, 전체 앱 중단 없음 |
| T22 | 모바일 60개 배치·20회 공간 전환 | 성능 예산 검증, 누적 리소스 누수 없음 |

### 15.2 테스트 계층

- 단위: 배치 충돌, 회전 footprint, 경로 탐색, 스키마 검증, 공개 정책, revision 처리.
- DB 통합: 실제 로컬 Supabase에서 사용자 A/B/외부/차단/방장 JWT로 RLS와 트랜잭션 검증. 서비스 역할로만 테스트하지 않는다.
- API 통합: 인증 누락, 입력 변조, 중복 키, 동시 저장·가입, 삭제 연쇄 처리.
- E2E: 생성자와 친구 두 브라우저 컨텍스트로 가입→공개→방문→댓글→알림 흐름.
- UI 검수: 360px·390px·768px·1440px, 200% 확대, 모션 감소, 긴 한국어 제목, 빈 데이터.
- 실기기: iOS Safari/PWA, Android Chrome/PWA, 데스크톱 Chrome·Safari·Firefox의 현재 안정 버전을 구현 시점에 기록하여 검수.

### 15.3 출시 게이트

- 핵심 흐름 E2E 통과, 권한·데이터 손실 결함 0건.
- RLS 활성화 확인, 비밀 키 프런트엔드 번들 노출 0건.
- 모바일 성능 목표 측정 결과 첨부. 미달 항목은 품질 조정 후 재검증.
- 접근성 대안 화면과 오류·빈 화면 준비.
- 에셋 라이선스 확인 완료, 초대 링크와 로그의 개인정보 노출 검사 완료.
- 백업·복구 절차, 오류 모니터링, 신고 처리 담당과 계정 삭제 절차 확보.
- 4~8명 파일럿에서 첫 전시와 상호 방문·댓글 완료. 사용자가 막힌 위치를 기록해 수정.

## 16. 운영·배포·리스크

- 개발/스테이징/운영 DB를 분리하고 프리뷰 배포가 운영 DB를 수정하지 않게 한다.
- CI는 lint, typecheck, 단위·통합 테스트, production build, 핵심 E2E 순서로 구성한다.
- migration은 스테이징에서 먼저 검증한다. 데이터 파괴가 있는 변경은 백업·복구 계획을 마련한다.
- 장애 로그는 requestId, 경로, 오류 코드, 처리 시간만 기본 수집한다. 원문 기록은 제외한다.
- 지표는 `onboarding_completed`, `archive_created`, `space_published`, `visit_opened`, `comment_created`, `save_failed`, `webgl_fallback` 등 최소 이벤트로 시작한다.
- 방문 이벤트는 운영 분석 목적의 최소 정보로 제한하고 개인별 방문 기록을 멤버에게 공개하지 않는다.

| 리스크 | 대응 |
|---|---|
| 공간 편집 기능이 범위를 크게 늘림 | 그리드·90도 회전·고정 슬롯·수량 제한 |
| 모바일 3D 성능 부족 | 공간 분리, 저품질 기본값, instancing, 목록 대안 |
| 정체성 옵션이 과도한 개인정보 수집으로 연결 | 선택 입력, 공개 범위 분리, 성별 분류 불필요 |
| 친구 사이 갈등·댓글 악용 | 차단·숨김·신고·탈퇴, 권한 테스트 |
| 외부 표지·브랜드 자산 문제 | 자체 일반 소품, 외부 이미지 수집 제외 |
| AI 비용과 실패율 증가 | MVP 제외, 기존 에셋 제안부터 검증 |
| 실시간 권한 회수 누락 | Phase 2 서버 게이트웨이·수신자별 정책 검증 |
| 에셋 교체로 기존 공간 깨짐 | 에셋 버전 고정, 장면 스키마 마이그레이션 |

## 17. Codex에 바로 전달할 개발 프롬프트

아래 블록을 이 파일과 함께 새 개발 작업에 전달한다. 이 문서는 개발 기획서이며 현재 단계에서 배포나 외부 계정 생성을 실행하라는 요청이 아니다.

### 17.1 시작 프롬프트

```text
첨부한 「ISOLA 개발 기획서 v1.0」을 제품 및 구현 명세로 사용해 웹 서비스를 개발해 줘.

제품 목표:
바다 위 아름다운 섬에서 4~8명의 친구가 각자의 집과 정원을 꾸미고 책·영화·문장·위스키 기록을 전시하며 비동기로 방문하고 댓글을 남기는 서비스다. 1명부터 시작 가능하고 최대 정원은 8명이다. 쿼터뷰 로우폴리 3D와 모바일 웹/PWA를 지원한다. 아바타 외형을 성별에 따라 제한하지 않는다.

먼저 할 일:
1. 저장소, AGENTS.md, 기존 구현, 사용 가능한 실행 환경을 확인한다.
2. 기존 앱이 있으면 구조를 존중하고 불필요하게 새 프로젝트를 만들지 않는다.
3. 명세의 기본값을 적용한다. 중대한 정보 누락이 아니면 사소한 선택 때문에 멈추지 않는다.
4. 구현 계획과 현재 단계의 완료 조건을 짧게 제시한 뒤 실제 코드를 작성한다.
5. 라이브러리 호환성을 확인하고 안정 버전을 lockfile에 고정한다.

구현 순서:
- M0: 도형 기반 섬/실내, 직교 카메라, 이동, 모바일 입력, 목록 대안을 만든다.
- M1: 인증, DB migration, RLS, seed, 환경 설정, 테스트 기반을 만든다.
- M2: 실제 저장소를 사용하는 섬 생성→책 기록→전시→초대한 친구 방문→댓글의 수직 흐름을 완성한다.
- 그다음 명세의 M3~M6 순서로 범위를 확장한다.

필수 구현 규칙:
- 화면 데모로 끝내지 말고 서버 저장과 권한까지 연결한다.
- 원본 기록과 공간 배치를 분리한다.
- 초안과 공개본을 분리하고 revision 기반 충돌 감지를 구현한다.
- 멤버 정원, 초대 사용 횟수, 집터 배정은 트랜잭션으로 보장한다.
- API 검사 외에 RLS와 DB 제약을 구현하고 서로 다른 사용자로 검증한다.
- 프라이버시 기본값은 나만 보기이며 공개 전시는 명시적 선택으로 한다.
- private 데이터·초대 토큰·댓글을 서비스 워커 캐시에 넣지 않는다.
- 공간·기록·댓글 조회는 차단과 현재 멤버십을 검증한다.
- 실시간 멀티플레이, LLM 호출, 3D 생성, 결제, 미니게임은 구현하지 않는다.
- 검증된 에셋이 없으면 도형으로 진행하고 교체 가능한 manifest 구조를 만든다.
- 목록 모드로도 핵심 기능과 배치 폼을 사용할 수 있게 한다.
- 사용자 데이터 삭제나 운영 배포는 작업 범위를 확인하고 수행한다.

검증:
명세 T01~T22 중 구현한 단계에 해당하는 테스트를 실행하고, typecheck와 production build를 확인한다. 모바일 성능은 실제 측정값과 환경을 기록한다. 아직 측정하지 않은 목표를 달성했다고 말하지 않는다.

매 단계 결과:
변경 내용, 실행 방법, 검사 결과, 남은 제약을 간결하게 보고한다. 비밀 정보는 출력하지 않는다. 실제 기능과 mock 상태를 명확히 구분한다. 서버 자격 증명이 없으면 로컬 Supabase와 실제 migration으로 진행하고 외부 설정이 필요한 지점을 문서화한다.
```

### 17.2 M2 완료 검수 프롬프트

```text
현재 구현을 기획서 M2 수직 흐름 기준으로 검수하고 발견한 문제를 수정해 줘.

사용자 A가 섬과 책 기록을 만들고 공개 전시한다. A의 초대로 사용자 B가 가입하고 A의 공간에서 기록을 열어 댓글을 남긴다. A가 알림을 확인한다. 사용자 C는 섬 외부이므로 같은 URL이나 API로 접근할 수 없어야 한다.

추가로 두 탭 저장 충돌, 초대 중복 요청, 정원 초과 동시 가입, 비공개 전환 후 직접 API 접근을 검사한다. 권한 실패는 UI만 보지 말고 사용자 JWT로 API와 DB를 검증한다. 테스트를 실행한 결과와 아직 실행하지 못한 검사를 구분해서 보고해 줘.
```

### 17.3 Phase 2 착수 프롬프트

```text
비동기 MVP가 출시 기준을 통과한 상태에서만 실시간 이동을 추가한다.

먼저 같은 공간에 있는 두 계정과 차단된 세 번째 계정으로 Realtime 권한 스파이크를 만든다. 이동 메시지의 서버 인증, 속도·좌표 검증, 수신자별 차단, 강제 권한 회수, 재접속을 입증한다. 방 전체 broadcast로 차단 상대의 위치가 유출되지 않아야 한다.

기존 DB 기반 공개본·기록·댓글 API를 유지하고 위치 이벤트를 영구 데이터와 분리한다. 선택한 서비스가 즉시 회수와 필터링을 지원하지 못하면 인증된 WebSocket 게이트웨이를 사용한다. 검증 전에 전체 실시간 UI를 확장하지 않는다.
```
