# 개발 상태 · 2026-11-03

## 3D 노을 마을 · 이번 작업

- 승인된 비주얼 방향인 **동화적인 지중해 섬 + 자연광 기반 스타일라이즈드 리얼리즘**을 첫 3D 환경 패스로 반영했다. 아트 디렉션 키프레임과 제작·성능 기준은 `docs/art-direction/WORLD_VISUAL_DIRECTION.ko.md`에 기록했다.
- 평평한 모래 지형에 잔디 언덕, 인스턴싱 풀·꽃, 해안 관목, 3D 야자와 올리브나무, 이끼 바위, 클럽 화단과 랜턴을 추가했다. 바다 셰이더에는 얕은 수심 색, 해안 거품, 다중 파동과 석양 반사를 더했다.
- 낮은 석양 방향광, 하늘 보조광, ACES 톤 매핑과 공기 입자로 장면의 깊이를 조정했다. 모바일 세로 화면에서도 중심 동선과 하단 조작 UI가 겹치지 않는 것을 브라우저에서 확인했다.
- 기존 2.5D 광장을 React Three Fiber의 3D 마을로 교체했다. 원형 해변 지형, 돌길, 건물의 입체 구조, 부두, 바위와 야자수, 움직이는 바다를 한 장면에 구성했다.
- 클릭한 지점으로 카피바라가 걷고, 마우스·터치 드래그로 카메라의 좌우와 고도를 회전한다. 스크롤/핀치 줌과 방향키/모바일 방향 버튼을 지원한다. 카메라는 플레이어를 부드럽게 따라간다.
- 노을 하늘과 건물 전면·야자수는 이 프로젝트용 생성 이미지다. 모래·돌·목재·벽·지붕은 CC0 표면 텍스처를 사용한다. 앞·옆·뒤 걷기 캐릭터는 기존 투명 컷아웃을 3D 공간에 세운 상태이며 완전한 3D 리그는 아니다.
- WebGL이 없으면 기존 2.5D 광장을 표시한다. 클럽 내부도 기존 2.5D 장면을 유지한다. 건물과 이동 경계의 정교한 충돌, 모바일 실기기 성능 측정, 실계정 2인 동시 접속 검증은 남아 있다.

## 이전 2.5D 이동 개선 기록

- 기존 2D 카피바라 컷아웃을 앞·옆·뒤 방향별 두 걸음 프레임으로 교체했다. 기존 캐릭터를 참고해 생성한 6개 WebP 프레임을 사용하고, 이동 방향에 맞춰 프레임을 전환한다.
- 클릭/키보드 이동에 가속과 감속을 적용하고, 모바일 방향 버튼은 누르고 있는 동안 계속 이동한다. 캐릭터 위치에 맞춰 화면이 조금 따라 움직인다.
- 클럽 문까지 걸어가면 자동으로 실내로 전환한다. 마을의 건물과 클럽 무대 앞에서는 이동 가능한 범위를 좁혔다.
- 마을 바다의 빛과 클럽 조명을 가볍게 움직였다. `prefers-reduced-motion`에서는 배경 효과를 멈춘다.
- 이동 방향을 Realtime Presence/Broadcast에 함께 보낸다. 실계정 2인 동시 접속과 모바일 실기기 검증은 여전히 필요하다.
- 당시 버전은 **2.5D 시각 개선**이었다. 위 3D 마을 작업이 이후에 추가되었다.

## 카피바라 스토리 · 노을 마을과 카피바라 클럽

- 최종 서비스명을 **카피바라 스토리**로 정했다. 기존 데이터베이스 식별자와 `isola_` RPC 이름은 호환성을 위해 유지한다.
- 첫 화면은 더 단순한 노을 바다 마을로 교체했다. 중앙 클럽 입구와 카피바라 가드 모카를 따라 실내 클럽으로 들어가고, 마을로 돌아올 수 있다.
- 클럽에는 가벼운 춤 동작, 건배 제스처, 사용자 클릭 후 시작되는 자체 합성 하우스 비트를 추가했다. 음악은 자동 재생되지 않는다.
- 실계정 Realtime Presence/Broadcast는 같은 섬의 마을/클럽 위치를 구분한다. 샘플 이웃은 연출용 NPC다.
- 실제 캐릭터 방향별 애니메이션과 지형 충돌, 정식 음악 및 다중 계정 동시 접속 검증은 후속 과제다.

## 웹 우선 재전환 · 초기 버전

- 사용자가 모바일/데스크톱 웹 전체 화면에서 카피바라로 만나는 소셜 월드를 우선하기로 했다. Godot 앱 프로토타입은 보존하지만 현재의 주 개발 대상은 `src/` 웹앱이다.
- 첫 광장을 전체 화면 아트와 스티커형 가장자리 HUD로 교체했다. 데스크톱 클릭/방향키, 모바일 탭/방향 버튼으로 카피바라가 화면 위를 이동하고 세 가지 짧은 제스처를 사용할 수 있다.
- 취향·이웃·설정 등 정보 화면은 광장 풍경 위에 열리는 패널로 바꾸고, 모든 화면에 `광장으로` 복귀 버튼을 제공한다.
- 손님은 로그인 없이 샘플 섬에 들어갈 수 있다. 샘플의 다른 카피바라는 연출용 NPC이며 실제 접속자로 표시하지 않는다.
- 실계정 섬에는 구성원 전용 Supabase 비공개 Realtime 채널을 연결했다. Presence로 접속자를 표시하고 Broadcast로 이동과 제스처를 보낸다. `002_capy_realtime.sql`을 사용자 프로젝트에 적용했다.
- 당시 월드는 고품질 2.5D 배경 위에 캐릭터 스프라이트를 움직이는 시각 프로토타입이었다. 이후 3D 마을과 방향별 걷기 프레임이 추가되었으며 집 내부의 동일 품질 재제작은 남아 있다.
- 두 개의 실계정으로 동시 접속을 검증하는 E2E와 iOS/Android 실기기 검수는 남아 있다.

- 가로 미리보기의 화면 확장 설정을 조정해 플레이 영역에 불필요한 검은 여백이 생기지 않게 했다.

## 이번 커밋: 첫 알파 구현

브랜드를 **ISOLA(이솔라)**로 확정하고, 동화적이고 귀여운 파스텔 로우폴리 방향으로 구현했다. 전체 제품 기획의 공개 출시 완료가 아니라 핵심 비동기 흐름을 사용할 수 있는 첫 개발 버전이다.

### 구현·검증한 내용

- 랜딩, 섬 지도, 집·정원, 취향 서랍, 이웃, 알림, 설정 화면
- 도형 기반 3D 집·자연·아바타·소품, 탭 이동과 목록 대안
- 프로필·아바타, 기록 저장·수정·삭제·공개 범위, 검색·분류
- 배치·회전·좌표 이동·삭제·되돌리기/다시 실행, 초안 저장·공개, 전시 연결
- 섬 생성, 정원 8명, 가입·초대 만료/취소, 방장 이전·탈퇴
- 댓글·숨김·삭제, 앱 내 알림, 차단·신고 접수, 데이터 내보내기
- Supabase SQL migration, RLS, 보안 함수, 서버 검증, 요청 속도 제한
- PWA manifest, 로컬 아이콘, 개인정보를 저장하지 않는 서비스 워커
- 24개 단위/DB 테스트 통과, 타입 검사와 production build 통과
- 의존성 취약점 검사 0건 (확인 당시)
- 브라우저 수동 검수: 샘플 진입, 기록 저장, 소품 배치→초안 저장→공개

### 실제 Supabase 연결

- 사용자 제공 프로젝트에 001 migration을 SQL Editor로 적용했다. 기존 public 테이블 0개를 확인하고 진행했다.
- 12개 테이블(public 11개 + private rate_events 1개)에 RLS를 활성화했다.
- 공개 키만 `.env.local`에 설정했다. 환경 파일은 Git에서 제외한다. Secret key는 사용하거나 저장하지 않았다.
- 실제 REST API에서 미인증 items 읽기와 isola_state 실행이 각각 401 / SQL 42501로 차단됨을 확인했다.
- 대시보드에서 기본 인증 메일이 로그인 링크 방식이며, 커스텀 템플릿 수정은 별도 SMTP 설정이 필요한 것을 확인했다. 앱은 로그인 링크 자동 세션 복원과 OTP 입력을 함께 지원한다.
- 실제 이메일 수신·클릭과 두 실계정 친구 방문 시나리오는 사용자 확인이 남아 있다.
- SQL Editor 적용은 Supabase CLI migration history를 등록하지 않는다. 기존 프로젝트에 001 파일을 다시 실행하지 말고, CLI 전환 시 운영자가 이력을 맞춰야 한다.

### 남은 제품 범위

- 정식 GLB 에셋 24종 및 아바타 파츠 목표 수량 확장 (현재 도형 소품 8종)
- 유형별 세부 메타데이터(완독일/도수 등), 댓글 수정, 위스키 유형 숨기기
- 자동 저장 없음(명시적 초안 저장). 오프라인 편집·동기화 없음
- 문서의 독립 REST 경로 대신 RPC 사용. 화면도 첫 알파에서는 단일 라우트 내 탭 구조
- 모든 기록을 받는 초기 snapshot API를 커서 페이지네이션으로 분리
- 섬 외부의 집/나무 장애물 경로 탐색, WASD, 방향키 이동 확장 (실내 그리드 경로 탐색 구현)
- 신고 처리 전용 관리자 화면, 계정 삭제 자동 작업, 내보내기 재인증
- 전체 기능별 컴포넌트 분리와 서버 응답 스키마 검증 확장
- 최신 데이터는 앱 전환/포커스와 30초 재조회로 갱신. 즉시 권한 회수 알림용 실시간 채널은 없음
- 실시간 멀티플레이, AI, 결제, 미니게임은 후속 단계

### 추가 검증 필요

- 실제 메일 수신과 신규·재로그인 흐름, 두 계정 및 탈퇴 계정의 API 접근
- 실제 다중 세션 동시 가입·동시 공개 (PGlite는 단일 연결이므로 동시성 증거가 아님)

- 전체 스크린리더·대비·터치 영역·키보드 접근성 감사
- Playwright E2E 데스크톱·모바일 4개 시나리오 통과. 실제 Safari·iOS·Android 실기기는 별도 검증 필요
